#+title: Module map
#+startup: showall

Where each module belongs, decided item by item before anything moves
(BACKLOG.org, /Module map/).  This file is the plan; the move follows
it, by a script, with the weekly checks green before and after.  The
lint check =groups= reads the two tables below and reports, until the
move, what the plan would break.

* Principles
Taken from established practice in software design, each turned into a
rule a check can hold:

1. *By feature, not by kind of code.*  A module is one thing the user
   sees -- the bibliography, the journal metrics -- not "all menus" or
   "all hooks" ("package by feature" against "package by layer").  The
   module contract has said so since 2026-10-16: one functionality, one
   module.
2. *Dependencies point one way.*  A module may require modules of its
   own group and of lower groups, never of a higher one (Robert
   Martin's acyclic and stable dependencies principles).  Checked by
   =groups= on =MyPKS-Requires=, the hard dependencies; a guarded use
   (=fboundp= and kin) degrades without the other module and may point
   anywhere.
3. *What changes together, and what is always used together, is one
   module* (the common closure and common reuse principles): the reason
   to merge two modules.  A part that could be swapped for another is
   the reason to split one.
4. *Places that can be filled by one module or another are slots*
   (=MyPKS-Provides=, since 2026-10-25q), as Doom's completion modules
   are alternatives.
5. *The group says what a module is; =MyPKS-Optional= and
   =MyPKS-Default= say whether it loads.*  A module of 100 may be
   optional and start off: being in the lowest group means nothing
   else of the configuration is under it, not that everyone loads it.
   A module using another only when present (=fboundp= and kin) works
   without it, with less: the PDF viewer is such a case for citar.

* Groups
One folder per group, as Doom Emacs keeps its modules in category
folders; file names keep the group's hundred (=modules/300-notes-core/305-notes.el=),
so that a file names its group outside its folder too.  Every full
name stays unique: a feature name is global in Emacs.

A module goes in the group of the *first* question answered yes:

| Group | Name                | Question                                                        |
|-------+---------------------+-----------------------------------------------------------------|
|   100 | Emacs               | Does it change Emacs itself, whatever the notes?                |
|   200 | Foundation          | Can it not be turned off -- does everything else need it?       |
|   300 | Notes core          | Is it part of the daily way of writing notes?                   |
|   400 | Notes extensions    | Does it add or replace something optional in the notes?         |
|   500 | Look                | Does it set the default look?                                   |
|   600 | Look modifications  | Does it change the look 500 sets?                               |
|   700 | Output              | Does it make something outside Emacs: PDF, DOCX, sites?         |
|   800 | Overview            | Does it read the collection and report on it?                   |

Decided 2026-10-25: the eight groups, English names, 700 Output added
to the owner's first seven, slots from the start.

* The move
When every row is decided:
1. Merges and splits first, one per patch, each with its tests.
2. Then the move by a script: =git mv= (history kept, =git log
   --follow=), new names in =provide=, =MyPKS-Requires=, =init.el=, the
   tests, =with-eval-after-load=, =function_helper.org= and
   =my/modules-off= of each machine (an alias from the old names, so a
   saved setting keeps working).  The weekly checks green before and
   after.
3. Then =groups= blocks instead of advising, and checks folders against
   this table.
