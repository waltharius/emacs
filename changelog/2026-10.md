## Session 2026-10-24b — Deleting a note: always to the trash; strict answers in the deletion tests

### Why

From the outside audits of 2026-10-24, decided by the owner the same
day ("always to the trash"): a note git tracks was removed with
`git rm -f`.  Git can give it back only as it was at the last commit,
so whatever had been written since -- minutes or hours, between
automatic commits -- was lost for good.  The exit status of `git rm`
was not read either: with `.git/index.lock` present (a background
commit running) the note stayed on disk while the command said
"Deleted (git)" and killed the buffer.  And the tests' stand-in for
questions answered yes to any yes-or-no question, so a question added
to a deletion would have been answered in silence.

### What

- modules/05-notes.el:
  - `my/denote--delete-file` moves the file to the system's trash,
    tracked or not, and signals when the file is still there
    afterwards; git keeps the history, and the next automatic commit
    (`git add -A`) records the deletion.  `my/denote--remove`, its
    duplicate used by the overwrite of a move, is gone; the move calls
    `my/denote--delete-file`;
  - `my/denote-delete-note` saves unsaved changes of the note's buffer
    before trashing it, so the trash holds what was typed; a failure
    stops before any attachment is touched and keeps the buffer.
- tests/test-notes.el:
  - `my/notes-test--answering`: `:yes` is a list of answers, one per
    question; a question beyond it, or an answer left unused, fails the
    test, and without `:yes` no yes-or-no question may come.  The
    overwrite, unsaved-move and deletion tests use it;
    `delete-attachments-declined` uses it instead of its own `pop`,
    which answered no in silence once its list ran out;
  - new: a tracked note, changed on disk and with an unsaved line,
    deleted -- the trash holds the commit, the saved change and the
    typed line, git the committed version; a trash that refuses stops
    the deletion with an error, the note, buffer and attachment kept.
- tests/test-safety.el: `2.1-tracked-note-kept-by-git` became
  `2.1-tracked-note-to-trash`: the trash holds the uncommitted text,
  git the committed version.
- The two tracked-note tests failed on the code before the change.
- Shown to fail, one fault at a time: a permanent delete (8 tests); the
  unsaved text not saved first; an extra yes-or-no question before the
  deletion (5 tests, through the strict answers).
- Caught only in a pair (rule 15): a trash failure swallowed is held by
  the check that the file is gone; both taken out, the failure test
  fails.
- SAFETY.org 2.1 and finding F1; function_helper.org; README (git is no

## Session 2026-10-24a — 07-git: no pull on an uncommitted tree; conflict markers and a failed add stop the cycle

### Why

From the outside audits of 2026-10-24 (several models, reviewed with
the owner): `git pull --rebase --autostash` re-applies uncommitted
changes after a successful rebase, and when they touch the lines just
pulled git writes conflict markers into the file and still exits 0.
Reproduced here with git 2.43: exit 0, the file `UU`, the local
version in the stash list.  `my/auto-commit--busy-p` did not see that
state, so the next cycle's `git add -A` would commit the markers and
push them to the other machine.  When it happens: the start-up pull
after Emacs closed without its exit commit, or a file saved while the
background pull waits for the network.  The same audits found that a
failed `git add` was ignored and the cycle went on to commit and pull.

### What

- modules/07-git.el:
  - `my/auto-commit--unmerged-p`: git's list of unmerged paths
    (`git diff --name-only --diff-filter=U`); `my/auto-commit--busy-p`
    counts it, so such a repository is neither committed nor pushed;
    `my/auto-commit-pending` reports it as "files hold conflict
    markers", and the warning names the files and what to do;
  - the pull runs without `--autostash` and only on a committed tree:
    with changes not committed the result is `dirty`, "changes not
    committed yet, not pulled", and the next cycle commits, then pulls.
    A file saved between the check and the pull makes git itself refuse
    the rebase; that failure is reported as `dirty` too, not as
    "server unreachable";
  - a failed `git add` ends the cycle with "ERROR git add failed":
    nothing is committed, pulled or pushed.
- tests/test-auto-commit.el, 3 new tests (27 in all), on real git with
  a bare server and two clones: an uncommitted change on a line the
  other machine changed is not pulled and keeps exactly what was
  written, no markers, no stash; files left unmerged by `git pull
  --autostash` (run by the test, exit 0) are not committed or pushed,
  and the warning names them; a lock file makes `git add` fail and the
  cycle stops before the pull.  The 3 failed on the code before the
  change.  `my/ac-test-commit-waits-for-startup-pull` writes its note
  after the pull starts: a dirty tree is no longer pulled.
- Shown to fail, one fault at a time: unmerged files not counted as
  busy; the failed add not stopping; the markers not reported.  Each
  was caught.
- Caught only in pairs (TESTING.org, rule 15): the check for
  uncommitted changes before the background pull and the removal of
  `--autostash` hold each other (git refuses a rebase of a dirty tree
  without it); both taken out, the uncommitted-change test fails.
  Reporting a refused pull on a dirty tree as `dirty` is reached only
  when a file is saved between check and pull; taken out together with
  the check, the same test fails.
- SAFETY.org 3.1: the new clauses, tested.  function_helper.org: the
  pull runs on a committed tree; the new echo-area lines.

## Session 2026-10-20a — The dependency reader follows branches; the checkers get tests of their own

### Why

An outside audit of the hooks (2026-10-20, by the owner, with a CSV of
reproductions) found that the `modules` check -- documented as erring
towards hard dependencies -- read seven unsafe uses as guarded:

- `(if (fboundp 'f) nil (f))`: the call runs exactly when `f` is
  missing;
- `(when (not (fboundp 'f)) (f))`;
- `(when (or (fboundp 'f) t) (f))`: a test that cannot fail;
- `(when (fboundp 'a) (b))`: a guard on one name, a call of another;
- `(unless (fboundp 'f) (message ...)) (f)`: an `unless` that only
  warns and goes on;
- `(symbol-value 'v)`: a quoted name handed to what reads it;
- `(defvar my/path "somewhere")`: the reader dropped strings, so the
  definition looked like a bare `(defvar my/path)` and its uses were
  not seen at all.

The cause: a test made a span around its enclosing form, whatever the
branch, and strings were skipped rather than kept as items.

### What

- hooks/module_contract.py: the reader keeps strings and characters as
  items; `dependencies` walks each module carrying what the tests
  around a position have shown -- `facts` gives, for a condition and
  its truth, the names it shows present (`fboundp` and kin: the name;
  `featurep`: the module), through `not`, `null`, `and` (true), `or`
  (false).  `when`/`unless` bodies, `if` THEN and ELSE, `and`/`or`
  arguments, `cond` clauses, `when-let*`/`if-let*` bindings and bodies,
  `with-eval-after-load`, and the rest of a body after a `when`/`unless`
  that ends by leaving (`user-error`, `error`, `signal`, `throw`).  The
  name a test is given is no use; a quoted variable given to
  `symbol-value`, `default-value`, `eval` is a read.
- 24-readwise.el: tests `my/zettel-reparent` as well as
  `my/zettel-adopt` before calling both -- the only use in the modules
  the stricter reader found (a guard on one name, a call of another;
  harmless today, as both come from 22-zettelkasten.el).
- tests/hooks/test_module_contract.py (new, Python unittest, 31 tests):
  a provider and a consumer for each case -- 15 guarded, 12 hard, 4 on
  what counts as a definition; the audit's seven among them.  With the
  reader of 2026-10-19, 13 of the 31 fail; with this one, none.
- hooks/check-all: runs `tests/hooks/test_*.py` after lint ("hook
  tests").
- function_helper.org (*Dependencies*), hooks/HOOKS-README.md
  (`modules`): which branch a test guards, and the tests.

### Decisions

- **A test guards the name it tests**, not its module: the audit's
  expectation, and the only reading that stays right when two
  functions of one module stop being defined together.  `featurep`
  still guards a whole module, since that is what it tests.
- **Tests in Python for checkers in Python**: the checkers are Python;
  ERT would test them only through a subprocess.

## Session 2026-10-18a — Personal dictionary in the settings folder, shared by every machine

### Why

Words added to the dictionary (`C-c S`, the fourth most used command
by keyfreq) stayed on the machine where they were added:
`~/.hunspell_personal` is outside both the configuration repository
and the settings folder.  Each machine therefore kept underlining the
words the other one had already accepted.  Asked for: the personal
dictionary in the settings folder (`~/.config/mypks` by default), so
that it travels between machines with the settings.

### What

- 03-spelling.el, section *Personal dictionary*:
  - `my/spell-personal-dictionary` (Writing → Spelling, new group
    `my/spelling`): `<settings folder>/dictionaries/hunspell_personal` by
    default.  At the root of the settings folder, not under
    `hosts/<host>/`: shared data, one file for all machines.  A change
    applies at once (`my/spell--dictionary-apply`).
  - Old words brought over (`my/spell--dictionary-prepare`): entries the
    new file lacks are appended, in order, from the file this machine
    used last (recorded in `hosts/<host>/spelling.eld`, so a change of
    the settings folder or of the option is followed) and from
    `~/.hunspell_personal`, once per machine.  Old files are only read.
    A report says how many words came from where and whether git carries
    the file.
  - `.gitattributes` beside the file: `hunspell_personal merge=union`.
  - A file watch on the dictionary's folder (`filenotify`): a word
    pulled from the other machine reaches the running Hunspell as `@word`
    (accepted for the session); a removed, forbidden (`*word`) or
    flagged (`word/FLAGS`) entry stops Hunspell, which rereads the file
    at the next check.
  - `my/spell-edit-personal-dictionary`, `e` in the Spelling column of
    `C-c n t`: opens the file to remove a word added by mistake; saving
    applies it.  The quit-time suppression of the dictionary buffer
    (`my/spell--personal-dict-buffer-p`) no longer applies to a buffer
    opened this way, so unsaved edits are asked about.
  - The file is no longer created at load with an aspell header
    (`personal_ws-1.1 pl_PL 0 utf-8`): Hunspell's personal dictionary has
    no header and read that line as a word.  The header is dropped when
    words are brought over.
  - `WORDLIST` replaces `HUNSPELL_PERSONAL`: Hunspell reads `WORDLIST`
    in place of `-p`; nothing reads `HUNSPELL_PERSONAL`.
- tests/test-spelling-dictionary.el (new, 15 ERT tests): format,
  merge, the attribute, once-per-machine import, a move, and what a
  changed file sends to a running Hunspell.  Runs without the rest of
  the configuration and without packages.
- function_helper.org: *Personal dictionary in the settings folder*
  (`#fn-spell-personal-dictionary`), `e` in the Spelling table, the
  settings folder table, Spelling in the settings tree.
  08-keybindings.el: `e` in the menu tree of the help text.
  TESTPLAN.org: R18.  BACKLOG.org: the files-the-modules-write entry
  (first shared file done), and the ordering constraint in the
  asynchronous-git entry.

### Decisions

- **Why two machines do not lose each other's words.**  Checked in
  Hunspell's source (`src/tools/hunspell.cxx`, `save_privdic`): the
  words added during a session are *appended* to the personal
  dictionary (`fopen(..., "a")`), and the list is cleared after the
  save.  A Hunspell running for days never writes back the words it
  read at start, so words pulled in meanwhile survive its next save.
  Appends from two machines between two cycles conflict at the end of
  the file; git's built-in `union` merge driver keeps both sides'
  lines.  Verified with git 2.43 on two clones: both an append/append
  conflict and an add/add conflict (both machines creating the file)
  resolve during `pull --rebase` without stopping.
- **When the old words are brought in: after the start-up pull.**  At
  module load the file is only *named*.  Creating it then would, on the
  second machine, leave an untracked file at the path the first
  machine pushed, and the start-up pull refuses to overwrite untracked
  files.  `my/desktop-after-startup-hook` runs after `after-init-hook`
  (where 07-git.el pulls synchronously), and depth -95 keeps it ahead of
  the release of Hunspell at -90.  Depends on the pull staying
  synchronous; noted in BACKLOG for the asynchronous-git work.
- **Once per machine for `~/.hunspell_personal`**, recorded in
  `spelling.eld`: merging it at every start would bring back a word
  removed from the shared file on purpose.
- **`@word` rather than a restart for new words.**  `@` is the ispell
  pipe command ispell.el itself uses to accept a word for the session;
  it has no output, so it does not disturb flyspell's reading of
  Hunspell's answers.  A restart costs the time to load pl_PL and
  en_GB-large again, at the moment typing resumes.  Removals cannot be
  undone with `@`, so they restart.
- **The folder is watched, not the file**: git replaces a file by
  renaming a new one over it, and a watch on the old file would stop
  seeing changes.
- **Rejected: a symlink `~/.hunspell_personal` → the new file.**  Works
  for Hunspell, but a symlink into the settings folder has to be made on
  every machine by hand or by NixOS, and replacing a regular file with a
  symlink is the kind of change to a user's home this configuration does
  not make on its own.
- **Rejected: no-littering for this file.**  no-littering moves state
  into `var/`, per machine; this file is shared data.  no-littering
  does not set `ispell-personal-dictionary` at all (checked in
  no-littering.el, main branch).

### Known limits

- The settings folder carries the file to another machine only when it
  is a git repository, or lies in the notes repository; the report
  says which applies.  Syncthing or another file synchroniser would
  also carry it, without the merge attribute.
- A file name containing whitespace gets no `.gitattributes` line
  (the pattern would need quoting); the default has none.

## Session 2026-10-14c — Reports that wait for an answer

### Why

  refusals offer to open the settings once Emacs is up

static file. Not reproduced: on TeX Live 2023 the same lookup succeeds
with static, mixed and variable-only installations, so the failure is

luaotfload's database rather than on the configuration.

## Session 2026-10-12e — Blog theme install: one at a time, never half-filled

### Why

After Session 2026-10-12d, the first sync of the docs site on the
laptop ended with `docs: theme hugo-geekdoc unpack FAILED`, and the
theme directory was gone.

### Cause

Two installs ran into the same directory. `url-copy-file` waits for the
download with `accept-process-output`, which lets timers run, so the

missing and both downloaded and unpacked it. Reproduced in batch Emacs

- The git clone moved into `my/blog--install-theme-git` and goes through

## Session 2026-10-12b — Pre-commit checks read only files git would commit

### Why

A rebase that only reset commit authorship was refused by the
pre-commit hook: `duplicates` reported 44 symbols defined twice. Every
second definition was in a Syncthing conflict copy in `modules/`
(`05-notes.sync-conflict-20261004-120707-G3DFVXZ.el` and thirteen
more). `.gitignore` excludes `*sync-conflict*`, so git never saw them,
and `init.el` loads modules by name, so Emacs never loaded them. Only
the hook read them: `lint.py` used `os.listdir` and `parens.el`
used `directory-files`. `parens (64 files)` was 50 modules plus 14
copies.

### What

Both scripts take their file list from `git ls-files --cached --others
--exclude-standard -- modules/`: tracked files plus untracked files that
are not ignored. `lint.py` gains `module_names`, which `modules` now
iterates; `parens.el` gains `parens--module-files`. Files tracked but
deleted from the working tree are filtered out, since `--cached` still
lists them. `core.quotePath=false` keeps non-ASCII names unquoted.
Outside a repository both fall back to the directory listing.

Verified in three states: an ignored conflict copy present (skipped,
`duplicates` passes), a new untracked module (read), and an archive
with no `.git` (fallback, all 50 modules read).

### Rejected

- **A name filter for `sync-conflict`.** Fixes this one producer of
  stray files and not the next one (an editor backup with an `.el`
  suffix, a file someone ignores deliberately). `.gitignore` is already
  the single place that says what is not part of the repository.
- **`git ls-files` without `--others`.** A new module would go
  unchecked until it is staged, which is exactly when a syntax error in
  it is cheapest to find.
- **Deleting the conflict copies and leaving the hook alone.** Removes
  the symptom; the hook would still check files that are not part of the
  configuration.

### Related

The conflict copies come from syncing this repository with Syncthing
while it also has git remotes. Synchronising a `.git` directory with a
file-level tool is the failure mode already avoided for `~/projects/`.
Taking the configuration out of Syncthing and relying on the GitLab and
GitHub remotes removes the source; this change only stops such files
from blocking commits.

## Session 2026-10-12a — Capture links, task dates, writing-mode indicator, hl-line, new note in tab

Six usability fixes collected from several weeks of use, in five
commits; the two capture points share one.  No commit depends on
another.

### Capture filing: no repeated source line (06-capture.el)

**Why.** Filing a capture under an existing heading always prepended a
`Source:` line. Three captures in a row from the same note produced
three identical labels, which `my/--note-fragment` already suppresses
on promotion but which cluttered captures.org itself.

**What.** `my/capture--subtree-last-source` returns the last source
recorded in the destination subtree: the last `Source:` body line, or
the heading's own `:SOURCE:` when the body has none.
`my/capture--fragment-from-entry` takes it as an optional argument and
omits the source line when `my/capture--source-key` of both is equal.
The destination marker is now resolved before the fragment is built,
since the fragment depends on it.

### Capture filing: directly below the last line (06-capture.el)

**Why.** The fragment was inserted after a blank line. A list item
typed as a capture therefore started a new list instead of continuing
the existing one.

**What.** Insertion point is the end of the last non-blank line of the
destination subtree, followed by a single newline and the fragment.
Numbering is not corrected; `C-u C-u C-c C-c` repairs it, and doing it
automatically would require deciding whether the fragment *is* a list
item, which is guesswork on free text. The whitespace that separated
the subtree from the next heading is kept, because only whitespace
before point is skipped.

### Capture: source link kept only on request (06-capture.el)

**Why.** Most captures are thoughts that occurred while some note
happened to be open. The automatic link to that note was rarely
meaningful.

**What.** `my/capture--ask-source` runs from
`org-capture-prepare-finalize-hook` at depth -10, before
`my/capture--ask-target`, and asks `Keep source link to «Title»?
(y/N)`. Anything except `y` deletes the `SOURCE` property from the
capture buffer before Org writes the entry. A capture from a buffer
with no file (the template writes `Untitled`) loses the property
silently. `my/capture-source-link-default` (new group `my/capture`)
inverts the default.

**Rejected.** `y-or-n-p`: no default answer, so RET cannot mean "skip".
Asking at capture start: interrupts the thought being captured, and
the template would need a `%(...)` expansion with side effects. Removing
`SOURCE` from the template: the origin would no longer be visible while
writing, and the decision is better made with the text on screen.

**Known consequence.** On promotion, `my/capture--split-into-segments`
attributes an unlabelled fragment to the last `Source:` line above it.
A fragment filed without a link under a heading whose last source is
another note is therefore credited to that note.

### Task date prompt: `other date` first (37-tasks.el)

**Why.** `other date` appeared last although it is the most used
answer.

**Cause.** Two things, not one. The completion table was a plain list,
so Vertico applied `vertico-sort-function` (history, length, alphabet)
and the defcustom order was never shown. And Vertico always moves the
default candidate to the top (`vertico--move-to-front` in
`vertico--recompute`), so the first visible entry is necessarily the
RET answer.

**What.** `my/tasks--read-date` uses a completion table declaring
`display-sort-function` and `cycle-sort-function` as `identity` (the
pattern already used in 33-denote-hubs.el), and
`my/tasks-date-choices` starts with `other date`. RET therefore opens
`org-read-date`; `none` is the second entry. The prompt names the RET
answer from the first entry instead of a hard-coded `none`.

**Rejected.** Keeping `none` as default while listing `other date`
first: impossible under Vertico without fighting its front-moving of
the default.

### Writing mode visible in the mode line (01-ui.el, 13-centered-writing.el)

**Why.** The indicator `W` existed but sat in `mode-line-misc-info`,
after every minor-mode lighter. In Org buffers, especially in split
windows, that is past the window edge, so the mode appeared to have no
indicator.

**What.** 01-ui.el gains a second seam, `my/mode-line-front-segments`,
rendered first in `mode-line-format` by `my/mode-line-front-render`.
13-centered-writing.el adds its construct there when the seam exists
and falls back to `mode-line-misc-info` otherwise. The label is now
`✍ Writing` instead of a single letter.

**Pitfall avoided.** Placing the variable directly in
`mode-line-format` does not work: a mode-line list whose first element
is a symbol is the conditional `(SYMBOL THEN ELSE)`. The first draft did
exactly that and would have made an empty seam swallow the following
segment. Rendering through `format-mode-line` inside `:eval` avoids
the grammar entirely. Verified in a terminal frame (`emacs -nw`);
`format-mode-line` returns an empty string in `--batch`.

### Current-line highlight back to pink (09-theme.el)

**Why.** The line under point used to be pink and became nearly
invisible.

**Cause.** `modus-themes-preset-overrides-faint`, spliced into the
common overrides, sets `bg-hl-line` to `bg-dim`. The pink is
operandi-tinted's own `bg-hl-line`, `#f1d5d0` (confirmed in
modus-themes.el and matching the screenshots pixel for pixel).

**What.** `modus-operandi-tinted-palette-overrides` set to
`((bg-hl-line "#f1d5d0"))`. Modus builds a palette as `(append
THEME-OVERRIDES COMMON-OVERRIDES CORE)`, so the theme-specific entry wins
over the preset.

**Rejected.** An entry above the splice in the common list: the hex
value would also apply to the dark theme and every other Modus light
theme. `custom-set-faces` or `set-face-attribute` on `hl-line`: writes
the `user` theme, the mechanism this configuration removed because it
survives a light/dark toggle.

### New note opens in a new tab (05-notes.el)

**Why.** `C-c n c n` replaced the buffer it was started from, losing
the place in the note being read.

**What.** `my/denote-base` calls `tab-bar-new-tab` after all prompts
and before `denote`, controlled by `my/notes-new-note-in-tab` (default
t). An error or quit inside Denote closes the tab again and re-signals.
`my/markdown-new-note` wraps `my/denote-base` and inherits the
behaviour.

**Rejected.** Binding `display-buffer-overriding-action` to
`display-buffer-in-new-tab` around the `denote` call: it would also
redirect any other buffer Denote displays. `other-tab-prefix`: acts on
the *next* command, not on a call inside the current one. Registering
the command in `my/fixed-tab-commands` (23-fixed-tabs.el): that routes
to one named, reused tab, while each note should get its own.

## Session 2026-10-02b — Spell checking: Polish dictionary must be UTF-8

### Why

After Session 2026-10-02a, *Messages* showed the real failure on every
attempt to enable flyspell:

    Error enabling Flyspell mode:
    (@(#) International Ispell Version 3.2.06 (but really Hunspell 1.7.2)
    error - iconv: ISO8859-2 -> UTF-8 ...)

with `my/flyspell-desktop-restoring` already nil. `ispell-init-process`
treats any output beyond the version line as an error, so flyspell
could not be enabled in any buffer. Before 2026-10-02a the release
called a bare `flyspell-mode-on`, which left the mode reported as on
with no post-command hook — the original symptom; since then
`flyspell-mode` switches itself off and says why.

The ISO8859-2 dictionary came back with the NixOS refactor:
`hunspell.withDicts` wraps the binary with
`--prefix DICPATH : <env>/share/hunspell`, so the store's `pl_PL` is
found before the UTF-8 copy in `~/.local/share/hunspell` that this
module put on `DICPATH`. Session 2026-10-02a ruled that out after a
test in an Ubuntu container, where the same Hunspell 1.7.2 converts
ISO8859-2 without complaint; the test environment did not reproduce
NixOS, and the conclusion should not have been drawn from it.

### NixOS repository

`modules/groups/emacs/home.nix` converts `hunspellDicts.pl_PL` to UTF-8
at build time (`hunspellPlUtf8`, a `runCommand`) and passes that
instead of `pl_PL` to `hunspell.withDicts`. The build fails if the
source is not declared ISO8859-2 or the result is not valid UTF-8.
`home.activation.hunspellUtf8` is removed.

Rejected: going back to the copy in `~/.local/share/hunspell`. With
`withDicts` the wrapper never reaches it; it would need plain
`hunspell` without dictionaries in the wrapper, and the activation
copy never refreshed anyway — store files have mtime 1, so its
`-nt` test was never true after the first run. A build-time conversion
is rebuilt with every nixpkgs update and covered by rollback.

### 03-spelling.el

- Both dictionaries are registered from the user profile only;
  `~/.local/share/hunspell` is no longer referenced. `DICPATH` keeps
  only the profile path, for a Hunspell without the wrapper.
- `my/flyspell--recheck-all-buffers` counts buffers where flyspell
  turned itself off and reports them in one `display-warning`
  (type `my/spelling`), pointing at the `iconv` cause, instead of an
  echo-area message per buffer.
- Comments rewritten: every dictionary must be UTF-8, and why.

### Verification

The `runCommand` script, run outside Nix against the LibreOffice
6.3.0.4 `pl_PL` that nixpkgs uses: both files UTF-8, header `SET
UTF-8`; Hunspell 1.7.2 through a `withDicts`-style wrapper checks and
suggests Polish words (`błendem` -> `błędem`) and accepts `colour`.
Batch Emacs 29.3: with that layout the startup release installs
`flyspell-post-command-hook`; with a Hunspell imitating the iconv
output, the "Error enabling Flyspell mode" message and the
`my/spelling` warning appear. Not verified: evaluation and build of the
Nix expression itself, and a real NixOS session.

### Follow-up

Leftover files in `~/.local/share/hunspell/` (`pl_PL.aff`,
`pl_PL.dic`) are unused and can be deleted.

## Session 2026-10-02a — Spell checking: live underlining lost after startup

### Symptom

Misspellings stopped being underlined while typing. `C-c n t S` and
`C-c n t b` still marked them, but every new error needed another
manual check.

### Cause

Both manual commands call `flyspell-region` / `flyspell-buffer`
directly, with the same Hunspell process and dictionaries as live
checking, so the dictionaries were not at fault. Live checking depends
on the per-buffer `flyspell-post-command-hook`, which only
`flyspell-mode-on` installs. The desktop-restore guard in
03-spelling.el sets the `flyspell-mode` variable and skips
`flyspell-mode-on`; when the guard is never released, every org/text
buffer reports flyspell as on while nothing checks, and `C-c n t T`
twice goes through the same guard and changes nothing.

The release (`my/flyspell--recheck-all-buffers`) runs from
`my/desktop-after-startup-hook`. That hook was run with `run-hooks`,
which stops at the first function that signals. `add-hook` prepends,
so 15-workspace.el, loaded after 03-spelling.el, put the dashboard
first: any error while rendering the dashboard prevented the release
for the whole session, visible only as "Error running timer" in
*Messages*. Reproduced in batch Emacs 29.3 with Hunspell 1.7.2: a
failing earlier consumer leaves `my/flyspell-desktop-restoring` at t,
the mode on and no post-command hook, also in buffers opened later.
Which consumer failed in the affected session was not established.

The NixOS dictionary change (`hunspell.withDicts`) was examined and
ruled out as the cause of this symptom; see "NixOS side" below.

**Correction (Session 2026-10-02b):** the diagnosis above was wrong.
The cause was the ISO8859-2 `pl_PL` brought back by
`hunspell.withDicts`; Hunspell on NixOS fails to convert it, unlike in
the Ubuntu container used for the test. The code changes of this
session stay; only the attribution was mistaken.

### 01-ui.el

`my/desktop--run-startup-hook` runs the hook through the built-in
`run-hook-wrapped` with the new `my/desktop--run-startup-function`:
each consumer's error is reported with `display-warning` (type
`my/desktop`) and the remaining consumers still run.
`condition-case-unless-debug` keeps `debug-on-error` usable.

### 03-spelling.el

- The release is registered at depth -90, ahead of every consumer at
  the default depth, independently of the isolation above.
- Buffers are re-enabled with `(flyspell-mode 1)` instead of a bare
  `flyspell-mode-on`. The minor-mode wrapper catches a failure and
  turns the mode off with a message, instead of leaving it reported as
  on; each buffer is additionally wrapped, so one failure does not stop
  the rest.
- `my/toggle-flyspell` releases the guard when it is still up, instead
  of toggling through it to no effect.
- Header and dictionary comments updated: the release no longer lives
  in 15-workspace.el, and the Hunspell activation moved to
  `modules/groups/emacs/home.nix` in the NixOS repository.

Rejected: moving the release back to `desktop-after-read-hook`, which
does not fire when no desktop file exists; dropping the guard, which
brings back one Hunspell start per restored buffer.

### NixOS side

`hunspell.withDicts` (nixpkgs `pkgs/by-name/hu/hunspell/wrapper.nix`)
wraps the binary with `--prefix DICPATH : <env>/share/hunspell`, so the
Nix-store `pl_PL` (ISO8859-2) is now found before the UTF-8 copy in
`~/.local/share/hunspell` that `DICPATH` set from Emacs points at; the
copy made by `home.activation.hunspellUtf8` is no longer used. With
Hunspell 1.7.2 and `-i UTF-8` this was tested to check and suggest
Polish words correctly, so it does not break spell checking, but it
makes the conversion dead code. Left unchanged here; to be decided
separately (plain `hunspell` plus `hunspellDicts.*`, or dropping the
conversion).

### Verification

Batch Emacs 29.3, Hunspell 1.7.2, NixOS-like `DICPATH` layout with the
`withDicts` wrapper imitated: with a consumer that signals placed
before the release, the warning appears, the guard is released and
`flyspell-post-command-hook` is installed; with the guard re-armed,
`my/toggle-flyspell` releases it. `check-parens` passes; byte-compile
adds no new warnings. Not verified: a real session with desktop
restore and the dashboard.

## Session 2026-10-01a — Auto-commit: pull before pushing, notes on two machines

### Why

The notes are now edited on two machines, a main laptop and a second
one for writing. Auto-commit only committed and pushed. The second machine kept
writing on top of the state it had when Emacs started: its push was
rejected, its automatic commits diverged from the server, and the only
trace was the `*auto-commit*` buffer, which nobody reads in an idle
cycle.

The notes travel through the local GitLab only. Syncthing on `~/notes`
was considered and rejected: it would also copy `.git/` while git is
writing to it, which can leave a broken repository, and on a conflict it
leaves `*.sync-conflict-*` copies to compare by hand, where git merges
changes to different lines and names the lines that collide. Syncthing
stays for `~/syncthing` (Zotero storage, the old Obsidian vault).

### 07-git.el

New option `my/auto-commit-pull` (t). Each repository is brought up to
date with `git pull --rebase --autostash`:

- **at startup**, from `after-init-hook` at depth -90, i.e. before
  `desktop-save-mode` reopens the last session's files (default depth),
  so buffers open on the newest version; every module is loaded by then,
  so the writing projects of 39-project-git.el are included;
- **before every push**, in the idle and exit cycles, after the commit,
  so a push never lands on an old state.

Rebase rather than merge: an auto-committed log would otherwise collect
a merge commit in nearly every cycle on the second machine. Files
changed by the pull are reloaded by `global-auto-revert-mode`
(02-editing.el); nothing new was needed for that.

`my/auto-commit--pull` returns `ok`, `offline`, `conflict`, `busy` or
`no-upstream`. A failed pull with a rebase in progress afterwards is a
conflict, any other failure is treated as the server being unreachable.

**Conflicts are never resolved automatically.** The rebase is aborted at
once, so the repository is exactly as before and no file holds conflict
markers; nothing is pushed; `display-warning` explains, once per
repository until a pull succeeds, what to do. Rejected: `-X ours` /
`-X theirs`, which resolve by silently dropping one side's text, and
leaving the rebase stopped, which the next idle cycle's `git add -A`
would have committed together with the markers.

**A repository with a rebase or merge in progress is skipped entirely**
(`my/auto-commit--busy-p`: `rebase-merge`, `rebase-apply`, `MERGE_HEAD`
under `git rev-parse --git-path`), so resolving a conflict by hand is
never interrupted by an automatic commit.

New commands: `my/auto-commit-pull-all` (what startup runs; reports
"updated from the server", "server unreachable, working offline",
"CONFLICT") and `my/auto-commit-resolve` (commit, pull by hand without
aborting, open Magit on the conflict). The cycle's echo-area summary now
lists `committed`, `pulled`, `pushed`, `server unreachable` and
`CONFLICT, not pushed`.

Rejected: an asynchronous pull at startup, which would let desktop
open buffers on the old content and then revert them under the cursor.
The synchronous pull costs at most the SSH `ConnectTimeout` (5 s) per
repository when the server is unreachable.

Verified in Emacs 29.3 in batch on two clones of one bare repository:
the machine behind pulls the other's commit; the same line changed on
both ends gives "committed, CONFLICT, not pushed", a clean file without
markers and one warning; an unreachable remote gives "committed, server
unreachable"; `my/auto-commit-pull-all` reports both. Byte-compiles
without new warnings. Not verified: against the GitLab over SSH,
the ordering against desktop restore in a real session, and
`my/auto-commit-resolve` with Magit.
