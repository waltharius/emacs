#+title: Testing: rules for the tests of this configuration
#+startup: showall

How tests are written here, and why.  Most rules come from something
that went wrong; the origin is named, so a rule can be dropped when its
reason no longer holds.  SAFETY.org says /what/ must hold; this file
says how a test shows it.  Running them: =bash hooks/check-all=
(hooks/HOOKS-README.md).

* Where the tests are
| Kind                         | Where                    | Runs                                            |
|------------------------------+--------------------------+-------------------------------------------------|
| Tests of modules (ERT)       | =tests/test-*.el=        | =hooks/check-all=, each file in its own =emacs -Q --batch= |
| Tests of the checkers        | =tests/hooks/test_*.py=  | =hooks/check-all= ("hook tests"), Python unittest |
| Sandbox for module tests     | =tests/helper.el=        | =my/test-load-modules=: temporary HOME, settings, =~/.emacs.d= |
| Packages for the workflow    | =tests/ci-packages.el=   | the workflow, before the tests                  |
| Weekly: every package needed | =tests/weekly/=          | =hooks/check-weekly=, and the workflow =weekly.yml= once a week |
| What only a person can check | =TESTPLAN.org=           | by hand, on the real machine                    |

* The rules
1. *A test shows that it can fail.*  A new test is run once with the
   safeguard or the function it tests taken out, and must fail then;
   the CHANGELOG entry says what was taken out and which tests failed.
   A test that passes either way checks nothing.  (2026-10-19, after
   the outside answer on checking code one does not read.)
2. *Assert the promise, not a sign of it.*  "Goes to the trash" is
   shown by the file being in the trash, not by it being gone -- a plain
   deletion makes it gone too.  (Audit of 2026-10-20: the old-files
   trash test.)
3. *A rule of several clauses is tested clause by clause*, and
   SAFETY.org says which clauses are tested and which are not.  A test
   file's name next to a whole rule claims more than it shows.  (Audit
   of 2026-10-20.)
4. *Nothing passes without having run.*  A check that cannot read its
   input says =skipped=, never =ok=; a selection matching no test file,
   or a file with no test, fails; skips are counted, and fail in the
   workflow, where nothing should be missing (=MYPKS_STRICT_TESTS=).
   (Audit of 2026-10-20.)
5. *A test that skips for long is a broken test.*  The menu test of
   notes-search skipped from the day it was written, and was wrong all
   along; it was found only when skips began to count.  A skip names
   its reason; a skip that is not about a missing program or package
   is fixed, not kept.  (2026-10-20b.)
6. *Positive and negative cases together.*  A checker is tested with
   what it must accept and what it must refuse -- the dependency
   reader with 15 guarded and 12 hard uses -- and with the misleading
   text that fooled it once: a key only in a comment, a name after the
   first =|=.  (Audit of 2026-10-20.)
7. *A checker that reads text says so.*  =keys=, =functions=,
   =codefolder=, =menus= recognise shapes of text; their description in
   HOOKS-README.md names the shapes, not the property they stand for.
   (Audit of 2026-10-20.)
8. *Tests never touch the real data*, and pass wherever the repository
   lies: modules load through =tests/helper.el=; a test that starts a
   second Emacs gives it a temporary HOME *and* starts it in a
   temporary folder (=default-directory=), since a current folder
   written as =~/...= means another place under another HOME.
   (2026-10-19s and x: green in =~/.emacs.d=, red on GitHub.)
9. *A test installs nothing and needs no network.*  Packages come from
   =~/.emacs.d/elpa/=; =use-package-ensure-function= is =ignore= in a
   test's Emacs.  (2026-10-19q: 77 s of network attempts per run.)
10. *The checkers have tests too*, in =tests/hooks/=: what a check
    reports is only as good as what it recognises.  (Audit of
    2026-10-20.)
11. *Test with the versions really in use.*  A test that reads a
    package's data passed with the transient built into Emacs and
    failed with transient 0.13, which the owner runs (it comes with
    Magit): the menu entry had another shape.  The workflow installs
    the archive transient (=tests/ci-packages.el=); a test reads data
    of a package through its documented interface, or tolerates every
    shape it has had.  (2026-10-20f.)  Again 2026-10-22: 12-transient's
    own reader of a menu entry knew only the built-in shape, so with
    0.13 a module switched off kept its menu entries; found by the
    weekly switch test, not by a test of 12-transient -- it had none.
12. *Test the first start, not only the later ones.*  A setup can
    behave differently in the session that installs a package: there
    the package is already loaded -- the byte compilation of its own
    files loads it -- before the module's own setup runs.  The tests
    of the PDF viewer's on-demand build loaded the module first, the
    order of every later start, and passed; the weekly first start
    then stopped on a question nobody could answer.  A setup that
    depends on what is loaded is tested in both orders.  (2026-10-23m
    and n.)
13. *A stand-in must outlive what it stands in for.*  A function
    replaced with =cl-letf= is replaced again when the file that
    defines it is loaded inside the test: the test of pdf-tools'
    loading counted no build because =pdf-tools.el= redefined the
    function and the real build started instead.  For a function of a
    package the test loads, the stand-in is advice (=advice-add
    :override=), which a redefinition keeps.  (2026-10-23m.)
14. *A tool's exit status, not its silence.*  =hugo --quiet= prints no
    errors; a build that failed on three relref shortcodes written in
    the change log looked clean, and was reported clean, until the exit
    status was read.  A check of an outside program reads its exit status, and
    says which one it read.  (2026-10-23j.)
15. *A planted fault nothing catches is a finding about the test as
    often as about the code.*  Either a second safeguard holds -- then
    both are taken out together, the test must fail on the pair, and
    the CHANGELOG says so (=save-match-data= in 47-repo-docs, held by a
    link check that no longer changed the match data) -- or the test
    does not reach the code it names: the first test of Denote links
    in Org pages let-bound =org-link-parameters=, which Org's parser
    does not read, so it never saw a Denote link at all; taking the
    branch out changed nothing, and that is how it showed.  The test
    is fixed before the code is believed.  (2026-10-23j and k.)

* Modules whose weekly tests are enough (2026-10-24)
Asked by the owner: does every module, the cosmetic ones too, need
tests of its functions?  No.  The weekly checks already test every
module: it loads alone, its switch goes off and on without a trace, it
compiles without a warning -- which catches what usually breaks such a
module (an error at start-up, a name gone after a package upgrade).
How something looks cannot be checked in batch anyway; TESTPLAN.org
holds that.  Tests of functions are for what a wrong answer costs:
modules that write, move or delete files, change the text of notes,
reach the network, or report something relied on.

A module that only changes how things look or behave on screen says
so in its header, =;; MyPKS-Tests: weekly=.  The lint check =tests=
then leaves it out of the modules without a test, and does not remind
of a test when it changes.  The =modules= check refuses the header on
a module whose code calls anything that changes files, runs a program
or reaches the network (=CHANGES_FILES= in =hooks/module_contract.py=;
it reads names in the code, not behaviour -- rule 7).  Not marked,
though they write nothing, because what they do matters: 02-editing
(it reloads buffers after a pull), 02b-bold-marker (it changes typed
text), 18-zotero-transient (it inserts formatted references),
32-web-links (network), 35-journal-gaps (a report relied on).

Marked on 2026-10-24: 03b-fonts, 09-theme, 10-visual-fill,
11-org-appearance, 13-centered-writing, 23-fixed-tabs, 30-link-tooltips,
34-appearance, 44-image-display, 45-standard-pages.

* Which module a test tests
Every test file starts with a header naming the modules whose
behaviour it asserts -- not every module it loads:

#+begin_src emacs-lisp
;;; test-safety.el --- ERT tests for the rules of SAFETY.org -*- lexical-binding: t; -*-

;; Tests: 00-core 05-notes 46-blog
#+end_src

The lint check =tests= (advisory) reads these headers: it lists the
modules no test file names, and, at a commit, a module staged without
any of its test files.

*Names say what and where.*  A failure is read first by its test's
name, so the name carries the module and the behaviour:
=my/<area>-test-<behaviour>=, e.g. =my/ns-test-parse-range-forms=,
=my/var-test-all=; a test of a SAFETY.org rule carries the rule's
number, =my/safety-test-2.1-no-answer-deletes-nothing=.  The docstring
says what is promised and, for a regression, what went wrong before.
One test asserts one behaviour, so that a red test points at one thing.

* Every module tested: the rule (2026-10-20)
Asked 2026-10-20: should every module have tests that show its
functions work, so that when something breaks it is clear what and
where?  Proposed in three parts, decided by the owner the same day:
(1) blocks once the repository is ready for people who only want a
note-taking program -- an installation guide and a tutorial that walk
them through the basics; until then the =tests= check reminds;
(2) yes, in the weekly job; (3) yes.

1. *A change to a module's behaviour comes with a test of it*, in the
   same patch -- or, for what cannot be checked in batch (how something
   looks, a window layout), a TESTPLAN.org item and a line in the
   CHANGELOG saying so.  A module marked =MyPKS-Tests: weekly= needs no
   test of its functions (part 2 below; decided 2026-10-24).  Checked today by the advisory =tests= check at
   each commit; *blocking* from the day the repository is ready for a
   first-time user (decided 2026-10-20).
2. *Every module has at least a load test*: it loads in the sandbox
   with all its packages, its switch goes off and on again without an
   error, its keys and menu entries come and go with the switch.  One
   test file for all modules, so a module that breaks is named by the
   test.  *Done 2026-10-22* (=tests/weekly/test-modules.el=, run by
   =hooks/check-weekly= and the weekly workflow): for each module of
   init.el's list, made from the list and the headers -- a module
   renamed, merged or split needs no change to the tests:
   - =alone=: 00-core, what the module declares, the module; nothing
     else.  A use of another module neither declared nor guarded
     fails.
   - =without= (optional modules): every other module but those
     requiring it loads.
   - =switch= (modules with a switch): loaded last, switched off and
     on.  Off, nothing of its own left -- hooks, advice, key bindings,
     menu entries, repeating timers, mode lists, capture templates,
     global minor modes -- and nothing of another module taken; on
     again, nothing doubled.  What the module's packages bring by
     being loaded is not counted (Emacs cannot unload a package), nor
     what the module defines (its own menus and keymaps stay, like its
     commands); =tests/weekly/lib.el= says how each is told apart.
   Shown to fail, one fault put in at a time: a hook added at load, a
   nameless hook, a timer started at each switch-on, another module's
   hook removed at switch-off, an undeclared call at load, the old
   menu-entry reader.  Known failures go in
   =tests/weekly/expected-failures.txt= with their reason; empty on
   2026-10-22.
3. *Modules that touch data get tests of their functions first*, in
   this order -- the order of SAFETY.org's risks: 05-notes (moving,
   renaming; done 2026-10-22h, =tests/test-notes.el=), 07-git (done
   2026-10-22j, =tests/test-auto-commit.el=), 27-denote-identifiers
   (done 2026-10-22k, =tests/test-denote-identifiers.el=),
   25-inbox-review (done 2026-10-22l, =tests/test-inbox-review.el=),
   26-maintenance (done 2026-10-23b, =tests/test-maintenance.el=),
   31-org-images (done 2026-10-23e, =tests/test-org-images.el=),
   39-project-git (done 2026-10-23f, =tests/test-project-git.el=),
   46-blog (SAFETY.org 1.1-1.4 and 1.6 done 2026-10-23g, in
   =tests/test-safety.el=), 47-repo-docs (several repositories,
   2026-10-23j, =tests/test-repo-docs.el=; Org and publishing follow),
   42-obsidian-import (done 2026-10-23r, =tests/test-obsidian-import.el=,
   with its script =tools/obsidian_import.py=), 24-readwise (done
   2026-10-23t, =tests/test-readwise.el=, SAFETY.org 3.2); then the
   others, a few per session, as each is next changed.
